2. 현재 1.5.3의 계통
======================================================================

개념적으로:

원작자 1.4.0
   ├─ 사용자 1.4.1
   │    └─ G1~G11 + H1~H7 장기방/무결성/UX 안정화
   │         └─ 사용자 통합 1.5.3
   │              + upstream 1.5.0 App Check / Vertex
   │              + upstream 1.5.1 UI polish/lazy rendering
   │              + upstream 1.5.2 Memory Diff
   │
   └─ 원작자 1.5.0 → 1.5.1 → 1.5.2

즉 1.5.3은 원작자 1.5.2를 통째로 수정한 것이 아니다.
사용자 1.4.1에 upstream 1.5.x 기능을 forward-port한 버전이다.

미래 upstream이 1.5.3/1.6.x로 올라가면:
- upstream 1.5.2 -> 새 upstream diff를 먼저 구한다.
- 그 diff를 BASE-153에 기능 단위로 forward-port한다.
- “새 upstream 파일로 교체 후 1.4.1 패치를 다시 얹기” 방식은 금지한다.

3. 반드시 보존할 1.5.3 핵심 계약
======================================================================

다음은 구현 세부가 아니라 regression contract다.
후속 패치는 같은 목적을 유지해야 하며 통째로 제거하면 안 된다.

----------------------------------------------------------------------
K01. Full Read 300/page + compatibility fallback
----------------------------------------------------------------------

- FULL_READ_PAGE_SIZE = 300
- legacy size = 50
- Crack 300 우선
- transient retry
- first-request incompatibility에서 Contents 50
- 필요 시 Crack 50
- host/cursor family를 읽기 도중 임의 혼합하지 않음
- retry count 3 계열 유지

왜:
장기방 request 횟수 감소 + compatibility 유지.

금지:
원작자 1.5.2의 50/page 전용 형태로 되돌리지 말 것.

----------------------------------------------------------------------
K02. Full Read safety bounds
----------------------------------------------------------------------

- FULL_READ_MAX_MESSAGES = 100000
- FULL_READ_MAX_PAGES = 1000
- repeated cursor 차단
- malformed role/id 차단
- duplicate id 차단
- pagination metadata 검증

금지:
“서버가 알아서 끝날 것”이라는 가정으로 guard 삭제 금지.

----------------------------------------------------------------------
K03. Physical Full Read single-flight
----------------------------------------------------------------------

- same rid + WishHistory.stamp 기준 physical read 공유
- caller는 subscriber
- subscriber 개별 cancel
- all subscribers cancel/stale일 때만 physical abort
- flight.aborted이면 새 caller를 old flight에 붙이지 않음
- aborting flight map detach 후 fresh physical 시작

과거 실제 regression:
마지막 subscriber cancel 후 old physical promise가 cleanup되기 전에 새 caller가 붙어 WISH_USER_ABORT를 상속하던 race가 있었음.
현재 fix를 유지할 것.

----------------------------------------------------------------------
K04. Cancel/stale/error 구분
----------------------------------------------------------------------

- user cancel: WISH_USER_ABORT
- room/route/restore/frontier/replay stale: WISH_HISTORY_STALE
- 실제 error와 cancel/stale을 diagnostics에서 분리
- cancelledReads / staleReads / errorReads 유지
- failedReads는 aggregate non-complete 의미 유지

----------------------------------------------------------------------
K05. WishHistory 12M / 36M
----------------------------------------------------------------------

- NORMAL_MAX_CHARS = 12000000
- HARD_MAX_CHARS = 36000000
- <=12M: deep snapshot
- 12M~36M: snapshotLarge top-level shallow-frozen
- >36M: uncached

금지:
>12M에서 cache miss 후 whole-history structuredClone을 다시 만드는 경로 추가 금지.

----------------------------------------------------------------------
K06. WishHistory monotonic revision / ABA 방어
----------------------------------------------------------------------

- hard revisions를 page lifetime 동안 작은 integer map으로 유지
- frontier sequence도 monotonic
- old revision을 eviction 후 implicit 0으로 되돌리지 않음
- Date.now 기반 ABA 가능 구조로 단순화하지 않음

----------------------------------------------------------------------
K07. Append frontier vs hard invalidation
----------------------------------------------------------------------

- 정상 POST /messages append는 soft frontier change
- edit/delete/message-specific mutation은 hard invalidate
- dirty frontier에서 hasMessage miss는 false가 아니라 unknown/null 가능
- recent overlap 검증 후 cache merge

----------------------------------------------------------------------
K08. Cache-first는 non-final에만
----------------------------------------------------------------------

cache-first 가능:
- preview
- export preparation
- analyze
- non-final source preparation

fresh physical 유지:
- final apply
- final commit
- authoritative source verification
- baseline-setting/critical verification

금지:
final integrity path를 cache-only로 최적화하지 말 것.

----------------------------------------------------------------------
K09. Initial injection giant full join 제거
----------------------------------------------------------------------

- full history는 branch/source validation에는 사용 가능
- recall context는 bounded context 사용
- 전체 stable RP를 다시 giant `.map(...).join()` 하지 않음

----------------------------------------------------------------------
K10. externalStageOnly
----------------------------------------------------------------------

- external AI JSON은 이미 AI 분석 결과임.
- 적용 stage에서 전체 RP를 다시 U3 prompt로 직렬화하지 않음.
- rows는 evidence/stage validation에는 유지.
- request envelope의 RP text는 omitted.

금지:
externalStage에서 multi-million char RP prompt 재생성.

----------------------------------------------------------------------
K11. External SOURCE strict integrity
----------------------------------------------------------------------

import/pre-session:
- source.last_message_id 비교
- source.sha256 실제 current source hash 비교

validated session:
- TTL 45,000 ms
- room + WishHistory.stamp + anchor + SHA 키
- 검증 후에만 session 저장

final external apply:
- fresh physical source
- anchor mismatch block
- strictExternalSource job에서는 SHA mismatch throw/block

주의:
내부/general R31의 non-strict notice semantics와
external import strict semantics를 억지로 하나로 합치지 말 것.

----------------------------------------------------------------------
K12. Cheap-first external JSON
----------------------------------------------------------------------

Full Read 전에 가능한 것:
- parse
- format/version/schema
- local semantic
- person/reference preflight
- recent anchor cheap check

그 뒤에만 expensive source read.

----------------------------------------------------------------------
K13. JSON repair / busy hold-resume
----------------------------------------------------------------------

- raw JSON memory 보존
- explicit resume
- polling 없음
- in-app editor <= 2,000,000 chars
- parse/schema/local semantic/source-format 등 repairable error만 editor
- actual source-content mismatch는 editor로 우회 금지
- retry 시 같은 validator를 다시 실행

----------------------------------------------------------------------
K14. Injection preparation cancellation
----------------------------------------------------------------------

- reading/validating phase cancelable
- Full Read subscriber/lock wait만 abort
- room.pending/save/PATCH/apply 시작 전 cancel boundary
- applying phase 진입 후 non-cancellable

----------------------------------------------------------------------
K15. WebSocket sendAttempted ordering
----------------------------------------------------------------------

정답:
previousSend.call(socket,data);
sendAttempted=true;

절대 금지:
sendAttempted=true;
previousSend.call(socket,data);

native send throw 시 sendAttempted=false 유지.

----------------------------------------------------------------------
K16. Delta one-shot fallback
----------------------------------------------------------------------

- WISH_DELTA_REJECTED일 때만 fallback
- 정확히 1회
- second request forceStateSnapshot=true
- unrelated failure에는 적용 금지
- retry loop 금지

----------------------------------------------------------------------
K17. STORE ZIP
----------------------------------------------------------------------

- STORE method(무압축 container)
- user explicit action에서만 생성
- progress
- cancel
- 개별 TXT 유지
- batch 10 유지
- zero-padded filenames
- giant all-text join 금지
- Blob/reference 중심

----------------------------------------------------------------------
K18. Backdrop gesture protection
----------------------------------------------------------------------

protected dialogs:
- JSON repair
- waiting/import
- review
- download
- 기타 중요 editor/sheet

동작:
- pointerdown/pointerup 동일 backdrop
- movement threshold 초과 시 close 금지
- drag/selection/scroll accidental close 금지

원작자 1.5.2의 단순 backdrop click close로 되돌리지 말 것.

----------------------------------------------------------------------

----------------------------------------------------------------------

보존:
- physicalReads
- completedReads
- failedReads
- cancelledReads
- staleReads
- errorReads
- pageAttempts
- fastAttempts

----------------------------------------------------------------------

현재 baseline:

11. 알려진 trade-off / 기술부채

T01. 코드 복잡도
- 1.5.3은 1.4.1과 upstream 1.5.x를 합쳐 세 버전 중 가장 큼.
- future merge 비용 증가.

T02. >36M uncached
- 의도적.
- memory safety 우선.
- repeated physical read cost 존재.

T03. STORE ZIP
- 무압축.
- CPU/메모리 부담을 줄이는 선택.
- 파일 크기는 줄지 않음.

T04. strict source mismatch
- 사용자 편의보다 correctness 우선.
- RP 변경 후 external result를 재사용하지 못할 수 있음.

T05. Vertex service account persistence
- private key가 포함된 JSON이 GM storage에 저장됨.
- 원작자 1.5.2 설계를 그대로 forward-port.
- future security hardening 후보.
- 즉흥 변경 금지; 독립 설계/회귀 필요.

T06. version metadata
- 작업상 1.5.3인데 현재 code header 1.5.2.
- 다음 코드 release에서 반드시 정리할 기술적 혼동 포인트.

13. 다음 AI가 먼저 해야 할 것
======================================================================

사용자가 “다음 패치 진행”이라고 하면:

1. 현재 1.5.3 파일을 직접 읽는다.
2. SHA/version 확인.
3. 사용자 요청이 live G10B인지 새 upstream merge인지 bug fix인지 분류.
4. live G10B라면 실제 증거가 있는 문제만 patch.
5. 새 upstream merge라면 upstream delta만 forward-port.
6. 수정 전 K01~K20 영향표 작성.
7. 수정 후 regression.
8. 결과 보고 시:
   - 무엇을 바꿨는지
   - 왜 바꿨는지
   - 어떤 contract를 보존했는지
   - 어떤 test를 통과했는지
   - 실제 브라우저 미검증이 무엇인지
   를 분리해 보고.

- 작업지시내용 = 사용자 1.4.1, 원작자 1.5.2, 사용자 통합 1.5.3 비교 결과를 다음 작업자가 AI에 재주입해 후속 패치에 사용할 수 있는 AI용 TXT 인수인계서로 작성.

- 불일치 상세 = 없음
