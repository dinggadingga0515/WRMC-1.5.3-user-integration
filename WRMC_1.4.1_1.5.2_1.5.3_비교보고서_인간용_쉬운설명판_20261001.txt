======================================================================
0. 세 버전의 관계부터 간단히 정리
======================================================================

[사용자 1.4.1]
원작자 1.4 계열을 바탕으로,
매우 긴 RP 방에서 멈춤·중복 조회·메모리 사용량 증가·잘못된 외부 결과 적용 같은 문제를
집중적으로 손본 사용자 패치 버전이다.

장점:
- 긴 RP 로그 처리에 강함
- 전체 로그를 반복해서 읽거나 복사하는 일을 줄임
- 외부 재구축 결과가 현재 RP와 맞는지 엄격하게 검사
- 취소·재시도·오류 진단이 강화됨

단점:
- 원작자 1.5.x에서 추가된 Vertex AI, Firebase App Check, 최신 UI, 새 Memory Diff가 없음


[원작자 1.5.2]
원작자가 1.5.0 → 1.5.1 → 1.5.2로 이어서 만든 공식 upstream 버전이다.

추가된 주요 기능:
- Firebase App Check
- Vertex AI
- 여러 설정창과 결과창의 UI 개선
- 기억 비교 화면(Memory Diff)의 가독성 개선

장점:
- 최신 AI 연결 기능이 많음
- UI가 정리됨
- 수정 전/후 비교 화면이 읽기 쉬워짐

단점:
- 사용자 1.4.1에서 따로 고쳤던 장기방 처리·중복 전체조회·일부 무결성 보호가 그대로 들어가 있지는 않음


[사용자 통합 1.5.3]
사용자 1.4.1을 바탕으로,
원작자 1.5.0~1.5.2의 좋은 기능만 다시 가져와 합친 버전이다.

즉 한 문장으로 정리하면:

“1.4.1의 장기방 안정성 + 원작자 1.5.2의 최신 기능/UI”

를 합친 것이 1.5.3이다.

======================================================================
1. 먼저 가장 쉽게 보는 핵심 변화표
======================================================================

아래 표는 개발자 기능명이 아니라 “사용자가 실제로 무엇을 체감하는가”를 기준으로 적었다.


기능 1. 아주 긴 RP 로그를 다룰 때 브라우저가 버벅이거나 멈출 위험

사용자 1.4.1:
- 1,200만자 이하: 전체 내용을 안전하게 복사해서 캐시
- 1,200만자 초과~3,600만자: 가벼운 방식으로 캐시
- 3,600만자 초과: 아예 캐시하지 않고 필요할 때 다시 읽음

원작자 1.5.2:
- 약 1,200만자를 기준으로 캐시 여부가 갈림
- 1,200만자를 넘는 큰 방에서는 캐시를 포기하는 구조가 중심
- 일부 경로에서는 큰 전체 로그를 다시 통째로 복사할 가능성이 있었음

사용자 1.5.3:
- 1.4.1의 1,200만/3,600만 구간 처리를 그대로 유지
- 1,200만자를 넘었다고 바로 전체를 무겁게 복사하지 않음

사용자가 체감하는 변화:
- 수천만 자 RP 방에서 “전체 로그를 한 번 더 통째로 복사”하면서 생기는
  순간적인 메모리 급증과 멈춤 위험을 줄이는 방향이다.
- 특히 1,200만~3,600만자 구간에서 1.5.2보다 장기방 반복 작업에 유리하다.

중요:
- 3,600만자는 “RP 로그 최대 길이”가 아니다.
- 3,600만자를 넘으면 사용을 막는 것이 아니라 “메모리에 오래 캐시하지 않는다”는 기준이다.
- 따라서 3,600만자를 넘는 방도 읽을 수 있지만, 반복 작업 때 다시 서버에서 읽는 비용이 커질 수 있다.


기능 2. 전체 RP 로그를 서버에서 읽는 속도

사용자 1.4.1:
- 정상 상황에서는 메시지를 한 번에 300개씩 읽음
- 300개 방식이 서버와 맞지 않으면 기존 50개 방식으로 자동 후퇴

원작자 1.5.2:
- 기본적으로 50개씩 읽는 방식 중심

사용자 1.5.3:
- 1.4.1의 300개 우선 + 50개 호환 방식 유지

사용자가 체감하는 변화:
- 같은 전체 로그를 읽을 때 필요한 서버 요청 횟수가 줄어든다.
- 이론적으로 같은 메시지 수라면 300개씩 읽는 방식은 50개씩 읽는 방식보다
  페이지 요청 횟수를 최대 약 1/6로 줄일 수 있다.

예:
- 메시지 60,000개라고 단순 계산하면
  50개씩 읽기 = 약 1,200페이지
  300개씩 읽기 = 약 200페이지

단,
실제 서버 응답 방식·분기·fallback에 따라 실제 호출 수는 달라질 수 있다.


기능 3. 서버가 잠깐 오류를 냈을 때 전체 작업이 바로 실패하는 문제

사용자 1.4.1:
- 네트워크 오류, 429, 5xx 계열처럼 일시적일 수 있는 실패는 제한된 재시도 적용

원작자 1.5.2:
- 이 부분이 1.4.1만큼 강화되어 있지 않음

사용자 1.5.3:
- 1.4.1의 재시도 정책 유지

사용자가 체감하는 변화:
- 전체 로그를 오래 읽다가 서버가 잠깐 흔들렸다는 이유만으로
  처음부터 다시 해야 하는 상황을 줄인다.

나쁜 점:
- 재시도하는 동안 실패 확정까지 시간이 조금 더 걸릴 수 있다.
- 무한 재시도는 하지 않는다.


기능 4. 서버 쪽 페이지 정보가 이상할 때 끝없이 읽는 문제

사용자 1.4.1 / 1.5.3:
- 최대 100,000개 메시지
- 최대 1,000페이지
- 같은 다음 페이지 주소가 반복되면 중단
- 잘못된 메시지 ID/역할/페이지 정보도 검사

원작자 1.5.2:
- 일부 반복 커서 방어는 있지만 1.4.1 수준의 전체 안전 상한은 없음

사용자가 체감하는 변화:
- 서버 응답이 비정상일 때 확장프로그램이 끝없이 페이지를 읽거나
  메모리를 계속 쓰는 상황을 막는다.

중요:
- 100,000개 메시지는 “정상 방을 여기서 잘라 버리기 위한 목표값”이 아니라
  비정상 서버 응답이 무한히 이어지는 일을 막는 안전장치다.


기능 5. 같은 전체 로그를 여러 기능이 동시에 읽을 때 중복 작업

사용자 1.4.1:
- 같은 방·같은 시점의 전체 조회 요청이 여러 개 들어와도
  실제 서버 전체 조회는 하나를 공유할 수 있음

원작자 1.5.2:
- 일부 내부 공유는 있지만
  모든 전체 조회 경로를 하나로 묶는 구조는 아님

사용자 1.5.3:
- 1.4.1 방식 유지

사용자가 체감하는 변화:
- 예를 들어 기억 갱신·재구축·검증 기능이 거의 동시에 전체 RP를 필요로 해도
  서버에 같은 대용량 로그를 여러 번 동시에 요청하는 일을 줄인다.
- 네트워크, CPU, 메모리 사용량이 모두 줄어드는 방향이다.

회귀테스트 예:
- 동시에 50개의 논리적 전체 조회 요청
- 실제 물리적 전체 조회는 1회로 수렴하는지 검사
- PASS


기능 6. 전체 조회를 취소했다가 바로 다시 실행했을 때 새 작업까지 같이 취소되는 문제

사용자 1.4.1:
- 취소 중인 옛 전체조회에 새 작업이 잘못 붙는 race를 수정

원작자 1.5.2:
- 이 사용자 패치가 없음

사용자 1.5.3:
- 수정 유지

사용자가 체감하는 변화:
- “취소 → 바로 다시 실행”을 했는데
  새로 시작한 작업이 이전 취소 상태를 물려받아 같이 실패하는 문제를 방지한다.


기능 7. 기억 주입을 준비할 때 전체 RP를 거대한 문자열로 다시 만드는 문제

기존 문제:
- 이미 전체 RP를 읽어 놓고도
  다시 모든 내용을 하나의 매우 큰 문자열로 합치는 경로가 있었음
- 수천만 자 방에서는 이 “한 번 더 합치기” 자체가
  메모리와 GC 부담을 크게 만들 수 있음

사용자 1.4.1:
- 전체 원문 검증용 데이터와
  실제 기억 검색에 필요한 짧은 문맥을 분리
- 전체 RP를 다시 거대한 문자열 하나로 만들지 않도록 수정

원작자 1.5.2:
- 해당 최적화가 사용자판만큼 들어가 있지 않음

사용자 1.5.3:
- 1.4.1 방식 유지

사용자가 체감하는 변화:
- 초장기방에서 “주입 시작 버튼을 눌렀을 때 갑자기 브라우저가 무거워지는” 원인 중 하나를 줄인다.


기능 8. 외부 AI가 이미 분석한 JSON을 적용할 때 전체 RP를 또 AI 요청문에 넣는 문제

사용자 1.4.1:
- 외부 AI가 이미 분석한 결과를 적용하는 단계에서는
  전체 RP 본문을 다시 AI 요청용 문자열로 만들지 않음

원작자 1.5.2:
- 일반 요청 경로를 타면서 전체 원문이 다시 직렬화될 수 있는 구조

사용자 1.5.3:
- 1.4.1 방식 유지

사용자가 체감하는 변화:
- 수천만 자 RP를 “이미 분석이 끝난 적용 단계”에서 또 정리하고 문자열로 만드는 낭비를 줄인다.
- 메모리 사용량과 적용 대기시간 감소를 기대할 수 있다.


기능 9. 외부 재구축 JSON이 현재 RP와 정말 같은 원문에서 만들어졌는지 확인

사용자 1.4.1:
- 마지막 메시지 ID뿐 아니라
  전체 원문의 SHA-256 지문까지 비교
- 최종 적용 직전에도 다시 확인

원작자 1.5.2:
- JSON 안에 SHA 필드는 존재하지만
  사용자판처럼 모든 외부 적용 경로에서 엄격하게 현재 원문과 일치하는지 막는 구조는 약함

사용자 1.5.3:
- 1.4.1의 엄격 검증 유지

사용자가 체감하는 변화:
예를 들어:
1. 오전에 전체 RP를 외부 AI로 보냄
2. 그 뒤 RP 원문 일부를 수정함
3. 오전에 만든 오래된 JSON을 오후에 적용하려 함

1.5.3은 원문 지문이 달라졌으면 적용을 막는다.

좋은 점:
- 다른 시점의 RP를 기준으로 만든 기억이 현재 방에 잘못 덮이는 위험 감소

불편한 점:
- RP를 조금이라도 수정했다면 다시 검증하거나 다시 만들어야 할 수 있음


기능 10. 같은 외부 JSON을 계속 검증하면서 전체 RP를 반복해서 읽는 문제

사용자 1.4.1:
- 한 번 정상 검증한 원문 정보는 약 45초 동안만 임시 재사용 가능
- 단, 방·원문 상태·마지막 메시지·SHA가 그대로일 때만 재사용

원작자 1.5.2:
- 이 짧은 검증 재사용 기능 없음

사용자 1.5.3:
- 1.4.1 방식 유지

사용자가 체감하는 변화:
- 인물 연결 창을 다시 열거나 수정 후 재시도할 때
  같은 수천만 자 RP를 바로 다시 전체조회하는 낭비를 줄인다.

왜 45초인가:
- 오래 보관해서 잘못된 검증 결과를 재사용하지 않고
  사람이 같은 작업을 바로 이어서 하는 짧은 구간만 재사용하기 위한 값이다.


기능 11. 잘못된 외부 JSON 하나 때문에 긴 RP 전체를 먼저 읽는 문제

사용자 1.4.1:
- JSON 문법
- 필요한 필드
- 인물 연결
- 로컬 의미 오류
등을 먼저 검사한 뒤,
정말 전체 RP 검증이 필요할 때만 Full Read 수행

원작자 1.5.2:
- 사용자판보다 비싼 전체조회가 앞쪽에서 실행될 가능성이 큼

사용자 1.5.3:
- 1.4.1 방식 유지

사용자가 체감하는 변화:
- 파일 자체가 잘못됐는데
  수천만 자 RP를 몇 분 동안 먼저 읽고 나서야 “JSON 오류”가 뜨는 일을 줄인다.


기능 12. 외부 JSON에 작은 문법/형식 오류가 있을 때 처음부터 다시 만들어야 하는 문제

사용자 1.4.1 / 1.5.3:
- 브라우저 안에서 JSON 수정창 제공
- 최대 2,000,000자까지 편집 가능
- 수정 후 같은 검증기를 다시 통과해야 함
- 실제 원문 불일치는 사람이 JSON을 고쳐서 억지로 통과시킬 수 없음

원작자 1.5.2:
- 이 수리 흐름 없음

사용자가 체감하는 변화:
- 쉼표, 필드, 일부 로컬 참조 문제라면 파일 전체를 다시 AI에 맡기지 않고 수정 가능

나쁜 점:
- 2,000,000자를 넘는 JSON은 브라우저 편집창을 열지 않음
- 너무 큰 JSON을 브라우저에서 편집하다 또 멈추는 문제를 피하기 위한 제한


기능 13. 다른 작업 중이라 외부 JSON을 적용할 수 없을 때 파일을 다시 선택해야 하는 문제

사용자 1.4.1 / 1.5.3:
- 가져온 JSON 원문을 메모리에 잠시 유지
- 다른 작업이 끝난 뒤 “계속”으로 같은 데이터를 재검증

원작자 1.5.2:
- 이 hold/resume 흐름 없음

사용자가 체감하는 변화:
- 대용량 JSON 파일을 다시 찾아서 선택하고 다시 읽는 번거로움 감소


기능 14. 주입 준비 중 취소 버튼이 제대로 작동하는가

사용자 1.4.1 / 1.5.3:
- 전체 읽기·검증 중에는 취소 가능
- 실제 서버에 적용하는 단계로 넘어간 뒤에는 중간 취소 금지

원작자 1.5.2:
- 준비 단계 전용 취소 구조가 사용자판보다 약함

원작자 1.5.2:

사용자가 체감하는 변화:
- 예를 들어 125개의 TXT가 나왔을 때

중요:
- 이 ZIP은 “압축해서 크기를 크게 줄이는 ZIP”이 아니다.
- STORE 방식으로 여러 파일을 한 컨테이너에 묶는 기능이다.
- 압축 CPU 비용을 줄이는 대신 ZIP 파일 크기는 원본 합계와 비슷하다.

회귀테스트:
- 125개 파일, 약 75MB 규모: PASS
- 300개 파일, 약 180MB 규모: PASS
- 생성 중 취소: PASS

“12~36M shallow cache”

쉬운 뜻:

기존 보고서의 표현:
“>36M uncached”

쉬운 뜻:
“3,600만자를 넘는 방을 금지하는 것이 아니라,
너무 큰 로그를 메모리에 오래 붙잡아 두지 않고 필요할 때 다시 읽는 방식”


기존 보고서의 표현:
“ABA 방어”

쉬운 뜻:
“예전에 시작한 느린 작업이 나중에 끝났다는 이유로
이미 최신 상태가 된 방을 과거 결과로 덮어쓰지 못하게 하는 장치”


기존 보고서의 표현:
“initial giant RP join 제거”

쉬운 뜻:
“이미 읽어 둔 수천만 자 RP를 주입 준비 중에 또 하나의 거대한 문자열로 합치는 낭비를 제거”


기존 보고서의 표현:
“externalStage RP 생략”

쉬운 뜻:
“외부 AI가 이미 분석한 결과를 적용할 때,
분석이 끝난 전체 RP를 다시 AI 요청문에 넣는 낭비를 제거”


기존 보고서의 표현:
“외부 JSON cheap-first”

쉬운 뜻:
“JSON 파일 자체가 잘못됐는지 먼저 싸게 검사하고,
정상 파일일 때만 비싼 전체 RP 조회를 실행”


기존 보고서의 표현:
“SOURCE SHA 엄격 검증”

쉬운 뜻:
“외부 AI 결과가 지금 화면의 RP가 아니라 예전 RP에서 만들어진 것이면
원문 지문(SHA-256)이 달라지므로 적용을 막는 기능”


기존 보고서의 표현:
“45초 source session”

쉬운 뜻:
“방금 확인한 똑같은 원문을 몇 초 뒤 다시 확인할 때
수천만 자 전체조회부터 다시 하지 않도록 45초만 검증 결과를 재사용”


기존 보고서의 표현:
“JSON repair / hold-resume”

쉬운 뜻:
“JSON에 고칠 수 있는 작은 오류가 있으면 프로그램 안에서 수정하고,
다른 작업 때문에 당장 적용 못 하면 같은 파일을 다시 선택하지 않고 나중에 계속”


기존 보고서의 표현:
“sendAttempted ordering”

쉬운 뜻:
“실제 전송이 성공한 뒤에만 프로그램도 ‘전송했다’고 기록하도록 순서를 수정”

“Delta 1회 full fallback”

쉬운 뜻:
“AI가 ‘변경된 부분만’ 보낸 결과가 특정 형식 오류로 실패하면

5. 1.5.3에서 오히려 나빠지거나 비용이 생기는 부분
======================================================================

1) 코드가 더 복잡함
장기방 안정화 코드와 원작자 새 기능을 모두 가지고 있으므로
유지보수해야 할 상태와 분기가 많다.

2) 원작자 새 버전을 그대로 덮어쓸 수 없음
앞으로 원작자 1.5.3/1.6.0 등이 나오면
새 변경점만 골라서 현재 1.5.3에 이식해야 한다.

3) 3,600만자 초과 방은 반복 작업이 느릴 수 있음
3,600만자를 넘는 로그는 메모리 안전을 위해 장기 캐시하지 않으므로
필요할 때 서버 전체조회를 다시 해야 할 수 있다.

4) 외부 JSON 적용이 더 엄격함
RP 원문이 바뀌면 과거에 만든 JSON을 그냥 적용할 수 없다.
편의성은 줄지만 잘못된 기억 적용을 막기 위한 의도적인 선택이다.

5) ZIP은 파일 크기를 줄여 주는 기능이 아님
STORE 방식이라 압축률은 거의 없고,
많은 파일을 한 번에 관리하기 쉽게 묶는 것이 목적이다.

6) Vertex 서비스 계정 저장 방식은 별도 검토 가능
현재는 원작자 1.5.2와 같은 방식으로
서비스 계정 JSON 설정을 저장한다.
보안을 더 강화하려면 별도 패치로 다루는 것이 좋다.
